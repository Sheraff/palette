# The round-page kit

**Status:** in use, 2026-08-04. Owns every new review page.
**Standing rule:** **no new review page is written outside the kit.** Adding a round means writing a
config object; if you find yourself calling `addEventListener`, `fetch`, or `normalizeKey` in a page
file, stop — the thing you are about to write already exists and is already tested.

---

## Why this exists

Three review pages shipped broken in three days. All three were the same failure in different
clothes:

| date | page | what shipped | why nobody caught it |
|---|---|---|---|
| 2026-08-03 | `/freetext` | `normalizeKey(event)` instead of `normalizeKey(event.key)` — the handler could never fire; the reviewer was stuck on cover 1 | 16 green tests, all of which drove the **server**; none loaded the module and pressed a key |
| 2026-08-04 | `/endorsement-recheck` | no working input surface; then an invented CSS class (`oracle-answer`) collapsed the hotkey grid into a run-on line | the harness has **no CSS engine**, so an unstyled class renders identically in tests and catastrophically in the browser |
| 2026-08-04 | `/endorsement-recheck` | no way to move between items without answering | nothing tested "can the reviewer look before deciding" |

None of these was a hard bug. Every one of them existed because each page re-implemented payload
fetch, navigation, key handling, hints, autosave, undo, resume and release from scratch — so every
page got a fresh chance to get one of them wrong. And **a page that renders is indistinguishable from
a page that works** until the reviewer sits down in front of it. `verify-live` cannot tell the
difference: it checks that a module is *served*, not that it *runs*.

The kit writes all of that once, and tests it once.

## Adding a round type

Three steps. There is no wiring step.

### 1. Markup — ids only, no key list

```html
<body class="oracle-body">
  <header class="oracle-bar oracle-head">
    <div class="oracle-prompt">
      <p id="preamble" class="oracle-preamble"></p>
      <p id="question">loading…</p>
      <p id="instruction" class="oracle-instruction"></p>
    </div>
    <p id="progress"></p>
  </header>
  <main id="stage" class="oracle-stage"></main>
  <footer class="oracle-bar oracle-foot">
    <ul id="mapping" class="oracle-mapping"></ul>
    <p id="pending" class="oracle-pending"></p>
    <p id="status">…</p>
    <!-- Generated by the kit. NEVER hand-write key names here. -->
    <p id="keymap" class="oracle-keys round-keymap"></p>
  </footer>
</body>
<script type="module" src="/your-round.js"></script>
```

### 2. The page

```js
import { enumKeys, imagePanel, startRound } from "./round-kit.js"

await startRound({
  batchKind: "oracle-validation",
  nodeIds: ["preamble", "question", "instruction", "progress", "stage", "mapping", "pending", "status", "keymap"],
  stimulusRenderer: imagePanel,
  answerWidget: enumKeys,
  unitSingular: "cover",
})
```

That is a complete round page. It fetches, resumes where the reviewer stopped, binds the fixture's
hotkeys, auto-advances, renders its own keymap, undoes, navigates, releases, and shows a visible
error if anything fails.

### 3. Route it

`batchReviewPaths` in `src/review-server/server.ts` decides which page a batch opens on — from the
**schema version**, not from `kind` alone. `kind` cannot tell two instruments apart.

## What the kit gives you

| concern | behaviour | the incident behind it |
|---|---|---|
| payload fetch | queue → payload; `?batch=` wins, else the newest unreleased round | — |
| failure | **always visible**: headline, status line, and an error panel in the stage. Never a permanent "loading…" | `/freetext` sat on "loading…" whenever anything threw — indistinguishable from a slow network |
| keys | shell takes the event, reads `.key` itself, **one `normalizeKey` call site**; widgets receive strings | `/freetext` passed the event object; every comparison was false forever |
| keymap | rendered every frame **from the same table the dispatcher reads** | endorsement's footer was hand-written and advertised keys the page had stopped binding |
| navigation | `j`/`k` and arrows, clamped, **records nothing** | endorsement had no way to see item 2 without answering item 1 |
| text fields | the field owns plain arrows and Shift+Enter; Escape leaves it; `c` returns | stealing an arrow makes a typo unfixable; stealing Shift+Enter makes a paragraph impossible |
| release | `r`, **never** from inside a text field, never sharing a key with an answer | a reviewer typing "red" must not end the round |
| autosave | debounce + blur flush; never writes an empty answer | `""` and "I see nothing" are different answers |
| undo | `u` / Backspace — steps back, deletes nothing; re-answering supersedes | the log is append-only |
| resume | opens at the first unanswered item | ten-minute chunks (REVIEW_UI §1) |

### Stimulus renderers

`imagePanel` · `textPanel` · `mockPlayer` (imports the **one** pinned `/mock.js`) · `composite(...)`

### Answer widgets

`enumKeys` (one keystroke, auto-advance) · `multiToggle` (toggle, commit on Enter/Space) ·
`freeText` (textarea, Enter saves and advances)

## Rules that are enforced, not suggested

1. **No `document.addEventListener("keydown")` outside the kit.** Checked by
   `review-server-round-kit.test.ts`, with a **shrink-only** grandfather list. Names come off it as
   pages migrate; nothing is ever added.
2. **Every class a renderer emits must match a real rule in `styles.css`.** Checked by walking what
   the page actually rendered — so it catches classes built from template strings, which a source
   scan cannot see.
3. **The payload allowlist is by construction.** `src/review-server/round-kit.ts` lists the fields a
   page may see; everything else is dropped with a reason attached. Adding a leak takes a deliberate
   edit a reviewer sees in a diff.
4. **The footer keymap is generated.** Hand-written key names in markup fail the test.
5. **Chrome is black and white, flat, no shadows** (REVIEW_UI §3). The artwork is the only thing
   allowed to carry colour.
