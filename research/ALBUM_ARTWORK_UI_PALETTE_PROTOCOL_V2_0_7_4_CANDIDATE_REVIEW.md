## Blinding And Ordering

Item order is fixed as listed above. Side assignment is independent for each item and uses no PRNG.

- Domain: `album-artwork-ui-palette-protocol-v2-0.7.4-candidate-review-1/side-assignment`.
- Message: canonical JSON with exactly `domain`, `protocolId`, `reviewVersion`, `sourceSha256`,
  `candidateTreatmentKey`, and `controlTreatmentKey`, with object keys sorted lexicographically and no
  insignificant whitespace.
- Digest: lower-case SHA-256 of the UTF-8 message.
- Assignment: the candidate is side A when the first digest byte is even; otherwise it is side B. The other
  side is the control.

The private manifest retains the digest and assignment. Before submission, the browser receives only an
opaque item token, ordinal position, opaque same-origin artwork URL, and side A/B presentation payloads. It
must not receive source case IDs, source paths, source hashes, treatment keys, version labels, candidate,
control, or baseline labels. Filenames, DOM IDs, network paths, comments, and static metadata must not reveal
assignment. Submission and storage use the same opaque item tokens; unblinding is not performed in the
browser.

## Complete-Treatment Presentation

Both sides use one `renderTreatment` browser function and the same markup and CSS. Each displayed treatment
must include:

- the same exact development artwork embedded borderlessly in the treatment field;
- background, surface, foreground, and accent visibly applied;
- a surface card and both foreground and accent over the field and surface;
- explicit flat/gradient status and legal surface/accent collapse status;
- a 135-degree background-to-surface CSS gradient with OKLab interpolation when `gradient` is true; and
- all four role labels, source hex values, generated status, collapse status, and nearest
  `colornames-oklab` names.

`colornames-oklab` `0.6.0` names are presentation-only metadata. They may not enter extraction, treatment
selection, side assignment, response interpretation, a gate, or any later inference. Outside complete
treatment previews and role swatches, the interface uses only black and white. Desktop and mobile use the
same renderer and payload.

## Response Schema

One submission covers both items. Every item requires:

- `qualityA` and `qualityB`, each exactly one of `strong`, `acceptable`, `weak-fallback`, `unacceptable`, or
  `uncertain`;
- `relative`, exactly one of `a-stronger`, `b-stronger`, `similarly-valid`, `neither-acceptable`, or
  `uncertain`;
- `issuesA` and `issuesB`, each a unique optional subset of `missing gradient`, `extraneous gradient`, and
  `incomplete artwork identity`; and
- `comment`, an optional string of at most 2,000 UTF-16 code units, preserved verbatim without trimming or
  normalization.

The blinded side-relative values map after server-side unblinding to candidate stronger, baseline stronger,
similarly valid, neither acceptable, or uncertain. The UI does not ask isolated-swatch questions.

The server accepts only a complete exact-schema submission bound to the review version, private-manifest
content ID, and both opaque item tokens. It adds an ISO timestamp and submission content ID, writes a temporary
file in the feedback directory, and publishes it with an atomic no-overwrite filesystem operation. If bound
feedback already exists, all further submissions receive a conflict response and the prior bytes remain
unchanged.

## Predeclared Analysis

No feedback analysis or technical interpretation is authorized during preparation. After human submission,
a separate read-only analysis step may:

1. verify the feedback raw hash, submission ID, private-manifest content ID, complete two-item denominator,
   exact response schema, and verbatim comments;
2. unblind side-relative responses and report complete counts for candidate stronger, baseline stronger,
   similarly valid, neither acceptable, and uncertain;
3. report absolute-quality counts separately for the candidate and control, plus side-mapped issue-tag counts;
4. reproduce every comment verbatim and keep any later agent-inferred technical interpretation in a separate
   field linked by comment hash; and
5. state the bounded, repeatedly exposed development limitation and make no population or Phase 4 claim.

This protocol predeclares descriptive analysis only. The review cannot by itself declare candidate support,
change inference, promote or freeze the candidate, open a protected sample, or advance a V2 phase. Any such
decision requires separate authorization after the human evidence exists.
